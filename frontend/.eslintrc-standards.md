# ESLint Coding Standards Documentation

This document explains the coding standards enforced by our ESLint configuration.

## Import Organization

**Standard**: Organize imports in the following order with blank lines between groups:

```typescript
"use client"; // If needed

// React/Next.js
import { useState } from "react";
import Link from "next/link";

// Third-party libraries
import { motion } from "framer-motion";
import { z } from "zod";
import { Mail, Lock } from "lucide-react";

// Local imports (absolute paths)
import { useAuth } from "@/context/AuthContext";
import { cn } from "@/lib/utils";
import api from "@/lib/api";

// Local imports (relative paths)
import { Button } from "./Button";
```

**Rationale**: Consistent import ordering makes it easier to scan dependencies and reduces merge conflicts.

## Export Patterns

### Components
**Standard**: Use default exports for page components and named exports for utility components

```typescript
// ✅ Good - Page component
export default function LoginPage() {
  // ...
}

// ✅ Good - Utility component (can be used either way, but prefer default for main components)
export default function Button() {
  // ...
}

// ✅ Good - Multiple utilities from one file
export function formatDate() {}
export function parseDate() {}
```

**Rationale**: Next.js requires default exports for pages. Using default exports for main components keeps the pattern consistent.

### Hooks
**Standard**: Use named exports for custom hooks

```typescript
// ✅ Good
export function useAuth() {
  // ...
}

// ❌ Avoid
export default function useAuth() {
  // ...
}
```

**Rationale**: Named exports make it clear what you're importing and prevent naming conflicts.

## Hook Return Values

**Standard**: All custom hooks should return a consistent interface:

```typescript
export function useCustomHook() {
  return {
    data: actualData,      // The main data
    loading: isLoading,    // Loading state
    error: errorMessage,   // Error message (string | null)
    refetch: refetchFn,    // Function to manually refetch
    
    // Optional: Action functions
    createItem: createFn,
    updateItem: updateFn,
    deleteItem: deleteFn,
  };
}
```

**Usage**:
```typescript
const { data, loading, error, refetch } = useCustomHook();

// Backward compatibility (if needed)
const { data: items, loading, error } = useCustomHook();
```

**Rationale**: Consistent interface makes hooks predictable and easier to use. Always returning these four core properties ensures proper loading and error handling.

## Error Handling

### API Calls

**Standard**: Always handle errors from API calls and use enhanced error properties

```typescript
// ✅ Good
try {
  const { data } = await api.post("/endpoint", payload);
  // Handle success
} catch (error: unknown) {
  const enhancedError = error as { userMessage?: string; message?: string };
  const errorMessage = 
    enhancedError.userMessage || 
    enhancedError.message || 
    "Operation failed";
  setError(errorMessage);
}
```

**Rationale**: The `api.ts` interceptor adds `userMessage` property with user-friendly messages. Using `unknown` type forces explicit type checking.

### Catch Blocks

**Standard**: Always type error parameters in catch blocks

```typescript
// ✅ Good
catch (error: unknown) {
  const message = error instanceof Error ? error.message : "Unknown error";
  handleError(message);
}

// ❌ Avoid
catch (error) {  // Implicit 'any'
  handleError(error.message);
}

// ❌ Avoid
catch (e: any) {  // Explicit 'any'
  handleError(e.message);
}
```

**Rationale**: TypeScript 4.4+ allows typing catch clause variables. Using `unknown` enforces proper error handling.

### localStorage Operations

**Standard**: Wrap localStorage operations in try/catch

```typescript
// ✅ Good
try {
  const data = localStorage.getItem(key);
  return data ? JSON.parse(data) : defaultValue;
} catch (error: unknown) {
  console.error("Failed to load from localStorage:", error);
  return defaultValue;
}

// ❌ Avoid
const data = JSON.parse(localStorage.getItem(key)); // Can throw
```

**Rationale**: localStorage can throw errors (quota exceeded, parsing errors, SSR). Always handle these gracefully.

## Async Patterns

**Standard**: Use async/await consistently, avoid promise chains

```typescript
// ✅ Good
async function fetchData() {
  try {
    const response = await api.get("/data");
    const processed = await processData(response.data);
    return processed;
  } catch (error: unknown) {
    handleError(error);
  }
}

// ❌ Avoid
function fetchData() {
  return api.get("/data")
    .then(response => processData(response.data))
    .catch(error => handleError(error));
}
```

**Rationale**: async/await is more readable and handles errors consistently.

## TypeScript Best Practices

### Type Annotations

**Standard**: Provide explicit types for function parameters and complex objects

```typescript
// ✅ Good
function processUser(user: User, options: ProcessOptions): ProcessedUser {
  // ...
}

// ✅ Good - Inferred return type is fine for simple functions
function add(a: number, b: number) {
  return a + b; // return type inferred as number
}

// ❌ Avoid
function processUser(user: any, options: any): any {
  // ...
}
```

### Avoid 'any'

**Standard**: Use `unknown` instead of `any` when type is truly unknown

```typescript
// ✅ Good
function handleUnknownData(data: unknown) {
  if (typeof data === "string") {
    return data.toUpperCase();
  }
  // ...
}

// ❌ Avoid
function handleUnknownData(data: any) {
  return data.toUpperCase(); // No type checking
}
```

## React Best Practices

### Component Structure

**Standard**: Organize component internals consistently

```typescript
export default function MyComponent({ prop1, prop2 }: Props) {
  // 1. Hooks (useState, useEffect, custom hooks)
  const [state, setState] = useState(initialValue);
  const { data, loading } = useCustomHook();
  
  // 2. Derived state / computed values
  const computedValue = useMemo(() => expensive(data), [data]);
  
  // 3. Event handlers
  const handleClick = useCallback(() => {
    // ...
  }, [dependencies]);
  
  // 4. Effects
  useEffect(() => {
    // ...
  }, [dependencies]);
  
  // 5. Early returns
  if (loading) return <LoadingSpinner />;
  if (!data) return null;
  
  // 6. Render
  return (
    <div>
      {/* ... */}
    </div>
  );
}
```

### Hook Dependencies

**Standard**: Always include all dependencies in useEffect/useCallback/useMemo

```typescript
// ✅ Good
useEffect(() => {
  fetchData(userId);
}, [userId]); // userId included

// ❌ Avoid
useEffect(() => {
  fetchData(userId);
}, []); // Missing userId
```

**Rationale**: Missing dependencies cause stale closures and bugs. ESLint rule `react-hooks/exhaustive-deps` catches these.

## Performance

### Avoid Inline Objects in JSX

**Standard**: Define objects/arrays outside render or use useMemo

```typescript
// ✅ Good
const style = { padding: 10 };
return <div style={style}>...</div>;

// ✅ Good
const style = useMemo(() => ({ padding: spacing * 2 }), [spacing]);
return <div style={style}>...</div>;

// ❌ Avoid (creates new object on every render)
return <div style={{ padding: 10 }}>...</div>;
```

**Rationale**: Inline objects cause unnecessary re-renders when used as props.

## Accessibility

### Alt Text

**Standard**: Always provide alt text for images

```typescript
// ✅ Good
<img src={url} alt="User profile photo" />

// ✅ Good - Decorative images
<img src={decoration} alt="" role="presentation" />

// ❌ Avoid
<img src={url} />
```

### ARIA Attributes

**Standard**: Use proper ARIA attributes for custom interactive elements

```typescript
// ✅ Good
<button
  onClick={handleClick}
  aria-label="Close dialog"
  aria-expanded={isOpen}
>
  <X className="w-4 h-4" />
</button>
```

## Code Quality

### Console Statements

**Standard**: Remove console.log, use console.error/warn/info for debugging

```typescript
// ✅ Good (for development debugging)
console.error("API call failed:", error);
console.warn("Deprecated feature used");
console.info("User logged in:", userId);

// ❌ Avoid in production code
console.log("Debug:", data);
```

**Rationale**: console.log clutters production console. Use proper logging tools for production.

### Prefer const

**Standard**: Use `const` by default, only use `let` when reassignment is needed

```typescript
// ✅ Good
const userId = user.id;
const items = [...originalItems];

// ✅ Good - needs reassignment
let count = 0;
count += 1;

// ❌ Avoid
let userId = user.id; // Never reassigned
var count = 0;        // Use let instead
```
